Wie setzt man taktisches Domain-driven Design (DDD) in Java um? In der
Folge zum taktischen DDD hatte Eberhard Wolff keinen Code gezeigt. Das
holt Oliver Drotbohm hier nach: Er ist seit über 14 Jahren im
Spring-Team, hat zehn Jahre Spring Data gemacht und stellt die
Bibliothek jMolecules vor. Mit ihr drückt man DDD-Konzepte direkt im
Code aus. Daraus lassen sich Regeln prüfen, Boilerplate-Code einsparen
und Dokumentation erzeugen.

## Wie jMolecules entstand

Ein Repository in Spring Data setzt ein Muster aus dem DDD um. Wer für
eine Entität ein Repository definiert, sagt damit implizit: Die Entität
muss ein Aggregate Root sein. Aus Diskussionen auf Konferenzen, unter
anderem mit Henning Schwentner, entstand die Idee, das explizit zu
machen. jMolecules ist Teil des Dachprojekts xMolecules. Dort gibt es auch Projekte für
PHP und .NET, die aber bei Weitem nicht so weit sind.

Eberhard schätzt an Spring Data, dass man nur fachlich sinnvolle
Methoden anbietet. Das ist für ihn der Kern des Repository-Patterns.

## Abhängig von einer Bibliothek

Eberhard wendet ein, dass die Geschäftslogik damit von jMolecules
abhängt. Oliver sieht das als Abwägung. Bei Annotationen kann man die Klasse
potenziell auch ohne die Bibliothek im Classpath verwenden und leicht wieder
umsteigen. Auch Joda Time hat man benutzt, und wenige hatten ein
Problem damit. Frameworks wie Spring liefern nur Annotationen, an denen sie
selbst interessiert sind; eine für Aggregates gehört nicht dazu.
jMolecules ist daher eine dünne Bibliothek, die nur die
Auszeichnungsmittel enthält. Man bindet sich nicht an eine Ablaufumgebung wie Spring.
Eberhard fragt nach der Alternative: eigene Annotationen oder
Namenskonventionen, aber ohne weitere Unterstützung.

## Regeln prüfen

In der Demo zeichnet Oliver eine Bestellung als Aggregate Root aus. Das
geht über Annotationen oder Interfaces. Einige Regeln prüft bei den Interfaces der Compiler allein
über die Typen: Ein Aggregate Root braucht zum Beispiel eine ID, die
Identifier implementiert. Für Annotationen und erweiterte Regeln gibt es den
APT, ein Annotation Processing Toolkit. Er erzeugt zusätzliche
Compiler-Fehler, etwa wenn ein Aggregate ein anderes als Objekt statt
über die ID referenziert. Das funktioniert in jeder IDE und auf der Kommandozeile.

Dieselben Regeln gibt es für ArchUnit und jQAssistant. Sie eignen sich
vielleicht besser, wenn man eine bestehende Codebasis Schritt für Schritt annähern will; der
APT ist strikt. In ArchUnit lassen sich vorhandene Verletzungen mit
Freeze zunächst festhalten. Eberhard erinnert daran, dass ein
fehlgeschlagener Test eine Einladung zur Kommunikation ist: Entweder
ergibt die Regel keinen Sinn, oder jemand hat das Konzept nicht verstanden.

## Code navigieren

Für IntelliJ gibt es den Prototyp eines Plugins. Er zeigt die Stereotypen an den Klassen und
gruppiert Klassen danach. Pakete, die alle Controller oder alle
Services sammeln, unterhöhlen für Oliver die Kapselung ein Stück weit. Findet man die Klassen über ihre Stereotypen,
kann man die Pakete nach fachlichen Modulen schneiden.

## Value Objects und Integrationen

Für beide ist eine E-Mail-Adresse kein bloßer String. Ein eigener Typ lässt nur gültige
Werte zu und bietet passende Operationen. Für Eberhard sind Strings
überall fast so wie das Anemic Domain Model: Es fehlt die Logik.

An den Rändern der Anwendung machen Value Objects aber mehr Arbeit. Sie müssen
in primitive Typen und zurück überführt werden, zum Beispiel für JSON oder URLs. Die Integrationen von
jMolecules für Jackson und Spring konfigurieren das automatisch. Liegt die
Bibliothek im Classpath, muss man die Klasse nur noch als Value Object auszeichnen.

## Persistenz

Aus einem Aggregate Root lässt sich ein großer Teil der JPA-Mappings ableiten:
die Entity, die ID, die One-to-Many-Beziehung zu den Bestellpositionen
samt Kaskadierung. jMolecules generiert das beim Build mit ByteBuddy
in den Bytecode. In der Klasse bleibt nur das Besondere, hier
der Tabellenname. Unterstützt werden JPA, MongoDB und Spring Data JDBC.

All das ist optional. Man kann auch nur die Typen benutzen, um die
Konzepte im Code sichtbar zu machen.

Vladimir fragt im Chat nach Lombok. Aus dem Java-Kernteam hört Oliver als Kritik an
Lombok: Es macht Quellcode lauffähig, der kein gültiges Java ist. Dafür greift es in die
Interna von Java ein. jMolecules generiert dagegen nach seinen Worten nur Metadaten und Code, der zur Compile-Zeit nicht
sichtbar ist. Wer das nicht will, muss es nicht verwenden. Für Frameworks wie Quarkus oder
Micronaut gibt es aktuell keine Integration; Pull Requests sind willkommen.

## Dokumentation

Spring Modulith nutzt die Konzepte von jMolecules, um Dokumentation zu
generieren: Komponentendiagramme und je Modul ein Application Module
Canvas. Es listet, was ein Modul nach außen zeigt, etwa Aggregates,
Services und Events. Auch das Javadoc kann einfließen. Die Teile
lassen sich als aktuelle Snippets in eigenen Text einbinden.

Zum Einstieg empfehlen beide das Demo-Projekt. Es enthält To-dos, mit denen man Schritt
für Schritt JPA-Annotationen entfernt.
