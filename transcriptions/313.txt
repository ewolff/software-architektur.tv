## Zusammenfassung

Tobias Wagner und Yadullah Duman von MaibornWolff setzen Coding Agents
in Kundenprojekten ein und geben ihre Erfahrung in Schulungen weiter. Im
Gespräch mit Eberhard Wolff und Ralf D. Müller berichten beide, was sich
mit den Agenten geändert hat, wo sie schneller geworden sind und welche
Best Practices sie vermitteln: Context Engineering, Workflows und
Harness Engineering.

### Drei Wellen bis zum Coding Agent

Yadu, wie Yadullah Duman meist genannt wird, hat in einem
Modernisierungsprojekt alle AI-Wellen erlebt. ChatGPT war für Yadu nur
ein Google-Ersatz mit kürzeren Feedback-Schleifen. Beim Chat-based
Programming mit Cursor, Windsurf oder Copilot Chat war das Ergebnis
nicht gut: Produktionscode brauchte viel Nacharbeit, besser lief es nur
bei einfachen Aufgaben wie Boilerplate und Testerstellung. Bis zu den
Coding Agents blieb Yadu Skeptiker, weil in Brownfield-Projekten viel
Wissen in einer komplexen Codebase versteckt ist. Mit Claude Code kam
der Wow-Effekt: Das Tool lebt im Projekt und bekommt dessen Nuancen über
Instruction Files mit.

Tobias Wagner nennt als weiteren Grund, dass die Modelle gelernt haben,
Tools zu nutzen: Sie lesen Daten, passen das Dateisystem an und
verlassen sich nicht mehr nur auf ihr internes Wissen. Auf Ralf D.
Müllers Frage, ob es an den Modellen oder am Workflow liegt, antwortet
Tobias: hauptsächlich an den Modellen. Yadu sieht einen Mix aus Modell
und Harness und erwartet, dass die Modellintelligenz irgendwann an eine
Wand stößt und die meisten Optimierungen dann im Harness passieren. Als
Opus 4.5 herauskam, war das für Yadu noch einmal ein Gamechanger. Beide
schreiben kaum noch Code von Hand.

### Wo die Arbeit schneller wird

Gemessen hat das Team nichts, Yadu hat aber aus der Tech-Lead-Brille
beobachtet. Die Analyse eines Bugs dauerte vor den Coding Agents meist
ein paar Tage. Mit Claude Code brauchte sie bei Bugs mittlerer Schwere
meist ein paar Stunden, und der Fix kam am selben Tag. Teilweise
kümmerte sich nur noch eine Person um Bugs statt zwei oder drei, die
Rolle rotierte im Team. Features landeten schneller in Produktion,
irgendwann übernahm eine Person ein ganzes Epic. Als Indikator nennt
Yadu, dass das Team vor den eigenen Schätzungen lieferte, und räumt ein,
dass das an den Schätzungen liegen kann. Um den Ist-Zustand eines Moduls
der alten Codebase zu verstehen, saß das Team früher zu fünft meist eine
Woche daran, bei einem komplizierten Modul anderthalb bis zwei Wochen.
Mit den Agenten schrumpfte diese Wissensextraktion auf fast einen Tag.

Tobias ergänzt, dass die Gewinne nicht gleichmäßig über alle Aufgaben
verteilt sind. Agenten kopieren vorhandene Patterns gut, schreiben
Automatisierungsskripte und machen Refactorings billiger. In einem sehr
komplizierten fachlichen Core helfen sie weniger, weil dort viel
Kontextwissen nötig ist. Eberhard Wolff nennt das eine starke
anekdotische Evidenz.

### Code Review bleibt

Im Projekt galt die Regel: Wer den eigenen Pull Request nicht erklären
kann, bekommt ihn nicht gemerged. Zuerst reviewte ein Subagent mit den
Review-Konventionen des Teams, dann die Person, die den Code generiert
hatte, auf GitHub schrieb ein Copilot Agent eine Zusammenfassung für den
menschlichen Reviewer. Weil das System auf kritischer Infrastruktur
lief, wurde jede Zeile gereviewt. Tobias macht die Tiefe des Reviews von
der Kritikalität abhängig: Bei unkritischem Code reicht meist ein
High-Level-Review, bei systemkritischem Code muss man sich jede Zeile
anschauen. Bei Security Reviews sieht Tobias die Modelle als
Sparring-Partner. Ob eine gemeldete Sicherheitslücke wirklich eine ist,
müssen weiter Menschen bewerten.

### Context Engineering

Das Context Window eines Modells ist begrenzt, und je voller es wird,
desto mehr Details vergisst das Modell. Das Phänomen heißt Context Rot.
Context Engineering hält den Kontext deshalb klein und relevant. Yadu
compactet lieber früh, damit der Agent fokussiert bleibt. Wer das
Context Window ausreizt, landet im Auto-Compacting, und dabei kann
Information verloren gehen. Tobias empfiehlt, die Compact-Funktion wenig
zu nutzen und stattdessen den Agenten die wichtigen Informationen in
eine Markdown-Datei schreiben zu lassen, die man in die nächste Session
mitnimmt.

### Workflows und Spec-Driven Development

Als Einstieg nutzen die Schulungen den Workflow Research, Plan,
Implement: drei Phasen in getrennten Sessions. Research und Plan liefern
je ein Dokument, Implement setzt den Plan um. Spec-Driven Development
stellt die Spezifikation stärker in den Vordergrund, als Beispiele nennt
Tobias Spec Kit und OpenSpec. Der Nachteil sind zwei Sources of Truth,
die auseinanderlaufen können. Ralf D. Müller zitiert Simon Browns
Einwand, Entwickler schrieben nicht gern Dokumentation. Yadu sieht das
genauso: Eine fast lückenlose Spec zu schreiben fühlte sich wie
Zeitverschwendung an. Tobias hat ein Team bei MaibornWolff gesehen, in
dem Specs als Austauschmedium zwischen Requirements Engineers und
Entwicklern dienen. Das scheint dort ganz gut zu funktionieren, auf dem
Detaillevel von Jira und nicht als Ersatz für den Code.

### Harness Engineering

Yadu erwartet, dass sich Human in the Loop zu Human on the Loop
weiterentwickelt. Harness Engineering heißt: Statt ein schlechtes
Artefakt selbst zu fixen, ändert man die Umgebung, die es erzeugt hat.
Tests, Linting-Regeln, Architektur-Tests und ein striktes Typsystem
geben dem Agenten Feedback und bestimmen, wie weit man ihn allein
arbeiten lassen kann. Tobias schreibt Skripte um die Testausführung, die
bei Erfolg nur einen Haken ausgeben, damit lange Stack Traces den
Kontext nicht füllen. Das spart Kosten, und die Session lässt sich
deutlich weiter treiben.

### Was Menschen weiter können müssen

Dass Entwicklerinnen und Entwickler komplett ersetzt werden, glaubt
Tobias nicht. Ein Harness aufzusetzen ist eine Aufgabe, die früher Tech
Leads und Architekten hatten, und braucht viel technisches Wissen. Für
Yadu ist AI ein Multiplikator: Agents kommen in guten Prozessen und
einer guten Codebase besser klar als in schlechten. Yadu rät, sich einen
Monat lang intensiv mit den Tools auseinanderzusetzen. Beide raten, sie
zum Lernen zu nutzen. Dazu gibt Yadu einen Satz von der AI Engineer
Konferenz mit: „Don’t outsource thinking.“

### Glossar

- **Context Window**: begrenzte Menge an Tokens, die in das Modell hineinpassen; im Gespräch früher meist 250.000 Tokens, mittlerweile eine Million als Standard
- **Compacting**: Zusammenfassen des Kontexts, wenn das Context Window voll wird; eine Lossy Function, bei der Information verloren gehen kann
- **Context Rot**: Das Modell vergisst mit der Länge des Chats immer mehr Details und macht mehr Fehler
- **Smart Zone und Dumb Zone**: Bild, mit dem Yadu Context Rot beschreibt; die Smart Zone liegt im Gespräch bei ungefähr 40 bis 60 Prozent des Context Window, darüber wird der Agent dümmer
- **Context Engineering**: Best Practices, um den Kontext des Modells klein und relevant zu halten
- **Research, Plan, Implement**: Workflow mit drei Phasen in getrennten Sessions; Research und Plan liefern je ein Dokument, Implement setzt den Plan um
- **Spec-Driven Development**: Kategorie von Workflows, bei denen neben dem Code eine Spec in natürlicher Sprache als Artefakt entsteht; Beispiele im Gespräch sind Spec Kit und OpenSpec
- **Harness Engineering**: Disziplin, die Umgebung des Agenten mit Feedback-Loops (Backpressure) so zu ändern, dass er beim nächsten Mal das Richtige produziert
- **Human on the Loop**: Weiterentwicklung von Human in the Loop, die Yadu erwartet
